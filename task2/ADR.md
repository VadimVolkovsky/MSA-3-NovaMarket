### <a name="_qmphm5d6rvi3"></a>**Решение**

Выбираем CQRS + EDA:
сервис Order History подписывается на Kafka-топики (Order*, Payment*, Shipment*, Inventory*, ReviewCreated) и
дублирует в свою ДБ историю заказов для отображения по запросу.
Чтение истории заказов происходит из ElasticSearch (или оптимизированной Postgres).

Преимущества:

- Быстрый отклик для UI (отдельная БД для чтения).
- Легко масштабируется
- Возможность добавления новых сервисов в будущем (лояльность, рекомендации, аналитика)

### <a name="_bjrr7veeh80c"></a>**Альтернативы**

API Composition

Описание: при запросе истории API Gateway собирает данные с Order Service, Payment Service, Shipping Service и т.д.
напрямую

Плюсы:

- Нет дублирования данных.
- Простая модель, сразу «свежие» данные.

Минусы:

- Высокая латентность (множество синхронных вызовов), трудно уложиться в SLA 0.3s/1s при росте трафика.
- Невысокая устойчивость — зависимость от доступности всех сервисов.
- Сложность кэширования и масштабирования

Вывод: непригодно для жестких требований SLA и масштабируемости в будущем.

**Недостатки, ограничения, риски**

- Возможна небольшая задержка обновления истории заказов (обычно <1–5s) — нужно донести до UX и согласовать с бизнесом.
- Дублирование данных: historyDB хранит копии основной БД с заказами, что потребует больше места и управляемых миграций.
- При большой нагрузке Kafka может отставать — нужно настроить мониторинг и алерты
